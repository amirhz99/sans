# مسئول سانس فوتبال ⚽

ربات فارسی بله برای مدیریت سانس، حضور، مهمان، بدهی و رسید پرداخت؛ با **Python 3.12+، SQLite و API هوش مصنوعی OpenAI-compatible**. بدون پنل وب، ORM، سرویس دیتابیس جداگانه؛ تنها وابستگی‌های pip مربوط به لایهٔ AI است و در `requirements.txt` آمده‌اند. اجرای فعلی برای Linux است.

هدف پروژه ساده است: یک گروه فوتبال دوستانه که هر هفته سالن می‌گیرد، باید بتواند با حرف زدن عادی — نه با فرم و پنل — سانس بسازد، بگوید چه کسی آمد، چه کسی مهمان آورد و چه کسی چقدر بدهکار است. ربات همهٔ این‌ها را از زبان فارسی می‌فهمد و هر تغییر مالی را پیش از ثبت، با یک کارت تأیید به ادمین نشان می‌دهد.

## اصل طراحی

هوش مصنوعی در این پروژه **یک درخواست‌ساز است، نه یک مجری**. مدل فقط می‌تواند «قصد» (Intent) بسازد؛ و هر Intent پیش از هر اثری اعتبارسنجی می‌شود:

```text
پیام کاربر → مدل → Intent → اعتبارسنجی → پیش‌فرض/پیشنهاد → کارت تأیید ادمین → دفتر کل
```

- قصد ناشناخته، آرگومان بدشکل، بازیکن ناموجود و سطح پاسخ نامعتبر **fail-closed** رد می‌شوند و هیچ اثری نمی‌گذارند.
- پول فقط پس از یک کلیک «تأیید» جابه‌جا می‌شود و هر تغییر یک ردیف دفتر کل با توضیح می‌گیرد.
- مدل هرگز فهرست کامل بازیکنان، شمارهٔ تلفن‌ها، محتوای رسیدها یا مقادیر `.env` را نمی‌بیند.

## امکانات

- مکالمهٔ آزاد فارسی برای ادمین و بازیکن؛ فرمان‌های جایگزین در زمان قطع AI.
- هزینهٔ کل زمین و سهم ثابت هر نفر، دو مبلغ مستقل برای هر سانس.
- ثبت حضور با تعداد مهمان؛ هر مهمان یک سهم کامل به حساب میزبان اضافه می‌کند.
- دفتر مالی تراکنشی: بدهی سانس، پرداخت، بدهی اولیه و اصلاح حساب با توضیح.
- پرداخت جزئی و بستانکاری؛ گزارش ماندهٔ هر سانس با تخصیص پرداخت‌ها به قدیمی‌ترین بدهی.
- توضیح عمومی پرداخت، توضیح شخصی بازیکن و یادداشت هر سانس.
- معرفی اولیهٔ کاربر، پیشنهاد تطبیق نام فارسی و اتصال حساب پس از تأیید ادمین.
- **اولین پیام هر کاربر تازه را خود ربات و بدون AI می‌فرستد**: نام و نام خانوادگی کامل و شمارهٔ موبایل را می‌خواهد؛ بعد از آن گفتگو به مدل می‌رسد.
- ثبت شمارهٔ تماس بازیکن با یک دکمهٔ «ارسال شمارهٔ من» و ذخیرهٔ آن در همان رکورد بازیکن؛ شماره‌ای که کاربر پیش از تأیید فرستاده، هنگام تأیید روی بازیکن ثبت می‌شود.
- ارسال عکس یا سند رسید به گروه، تأیید/رد ادمین و اطلاع به کاربر.
- حالت ثبت خودکار رسید، **خاموش به‌صورت پیش‌فرض**؛ بدون ادعای بررسی بانکی.
- نمایش بدهی هر نفر و گزارش کلی در گروه مدیریتی تنظیم‌شده؛ همهٔ اعضای همان گروه ادمین محسوب می‌شوند.
- پرسش دوره‌ای از ادمین‌ها دربارهٔ اطلاعات ناقص و یادآوری بررسی رسید/هویت.
- ورود CSV اولیه بدون حساب بله، بکاپ سازگار SQLite، تاریخچهٔ تغییرات و صف ارسال پایدار.
- پیام‌های پشت‌سرهم یک نفر در یک بازهٔ کوتاه به‌صورت **یک درخواست** پردازش می‌شوند و حافظهٔ گفتگو عمیق‌تر و کران‌دار است.
- **پیشرفت زنده**: پیام «دریافت شد» مرحله‌به‌مرحله ویرایش می‌شود و پاسخ در پیام جدا می‌آید.
- سانس برگزارنشده با یک کارت صریح بسته می‌شود، بدون ثبت هیچ بدهی.
- پیام مستقیم به مخاطبان ربات، با تأیید ادمین، و دریافت شماره با دکمه.

### متن‌ها و پیش‌فرض‌های قابل کنترل

متن prompt هوش مصنوعی، راهنمای کاربر و راهنمای ادمین، به‌همراه پیش‌فرض‌های ساخت سانس، همگی در فایل زیر قرار دارند:

`/opt/sans/content/bot-content.json`

پیش‌فرض فعلی برای سانس جدید:

- محل: **سالن فوتسال نمونه**
- هزینهٔ کل زمین: **۲٬۵۰۰٬۰۰۰ تومان**
- سهم هر نفر: **۱۵۰٬۰۰۰ تومان**
- فرمول بدهی: سهم هر نفر × (۱ + تعداد مهمان)

این مقادیر فقط مقدار اولیه‌اند: ادمین می‌تواند آن‌ها را با `/setdefault` تغییر دهد و با `/defaults` ببیند. مقدار ذخیره‌شده در جدول `settings` بر فایل `content/bot-content.json` اولویت دارد، و تغییر آن هم مثل بقیهٔ تنظیمات فقط با دکمهٔ «تأیید» اعمال می‌شود. اگر کارت ساخت سانس از پیش‌فرض استفاده کند، همان کارت صریحاً می‌نویسد کدام مقدار از پیش‌فرض آمده تا ادمین تأیید یا اصلاح کند.

ادمین می‌تواند برای هر سانس مقدار متفاوتی اعلام کند؛ مقدار صریح ادمین بر پیش‌فرض غلبه دارد. زمان دقیق استثناست و باید اعلام شود؛ عبارت‌هایی مثل «امروز عصر» ثبت نمی‌شوند و ربات ساعت دقیق را می‌پرسد. زمان‌های جدید در ستون `session_at` به‌صورت ISO با timezone `Asia/Tehran` ذخیره می‌شوند و عبارت اصلی کاربر در `when_text` نیز باقی می‌ماند. تغییر این فایل از سانس‌های قبلی یا بدهی‌های ثبت‌شده اثر نمی‌گیرد و برای بارگذاری متن جدید، سرویس را restart کنید. ادمین‌ها می‌توانند با `/config` تنظیمات فعلی، متن پرداخت، وضعیت تأیید رسید و قیمت سانس‌های باز را ببینند.

## راه‌اندازی

در بله از `@botfather` توکن بگیرید و ربات را به گروه خصوصی ادمین‌ها اضافه کنید. دسترسی دریافت پیام‌های گروه و ارسال پیام/عکس/فایل باید فراهم باشد. همهٔ افراد گروه را مورد اعتماد در نظر بگیرید، چون پاسخ‌های ربات برای تمام اعضای گروه دیده می‌شود.

```bash
cp /opt/sans/.env.example /opt/sans/.env
chmod 600 /opt/sans/.env
```

فایل `/opt/sans/.env` را تکمیل کنید:

| تنظیم | توضیح |
| --- | --- |
| `BALE_BOT_TOKEN` | توکن بله |
| `ADMIN_GROUP_ID` | شناسهٔ عددی گروه مدیریتی |
| `ADMIN_USER_IDS` | فهرست شناسهٔ عددی ادمین‌ها با کاما. فقط وقتی `ADMIN_ACCESS=allowlist` باشد اثر دارد و به همان کاربر در گفت‌وگوی خصوصی هم اختیارات ادمین می‌دهد |
| `ADMIN_ACCESS` | `allowlist` (پیش‌فرض: عضو گروه مدیریتی ادمین است و فقط شناسه‌های `ADMIN_USER_IDS` در گفت‌وگوی خصوصی هم ادمین‌اند) یا `group_members` (فقط گروه؛ در خصوصی هیچ‌کس) |
| `AI_BASE_URL` | آدرس پایهٔ HTTPS سرویس، معمولاً با انتهای `/v1`؛ نه مسیر کامل chat/completions |
| `AI_API_KEY` | کلید سرویس |
| `AI_MODEL` | نام مدل در همان سرویس |
| `AI_FALLBACK_MODEL` | اختیاری؛ نام یک یا چند مدل جایگزین با کاما. اگر مدل اصلی خطا بدهد (مثلاً سهمیه/۴۰۲)، همان درخواست با مدل بعدی تکرار می‌شود |
| `DATABASE_PATH` | پیش‌فرض: `/opt/sans/data/sans.sqlite3`؛ مسیر نسبی نسبت به ریشهٔ پروژه تفسیر می‌شود |
| `BOT_NAME` | پیش‌فرض: `مسئول`؛ واژهٔ خطاب در گروه |
| `REMINDER_HOURS` | فاصلهٔ یادآوری‌ها، پیش‌فرض ۲۴ ساعت؛ صفر یعنی خاموش |
| `SUPPORT_HANDLE` | اختیاری؛ آیدی پشتیبان انسانی مثل `@club_support`. ربات وقتی نتواند مشکل کاربر را حل کند یا او بپرسد «با کی صحبت کنم»، همین آیدی را می‌دهد و `/support` هم آن را نشان می‌دهد. خالی یعنی این قابلیت خاموش است و ربات به ادمین‌های گروه ارجاع می‌دهد |

متغیرهای محیطی سیستم بر مقادیر فایل اولویت دارند. فایل env ساده است و از expansion یا کامنت انتهای مقدار پشتیبانی نمی‌کند.

### به‌دست‌آوردن شناسه‌ها

فقط توکن را در `/opt/sans/.env` وارد کنید. هر ادمین در خصوصی ربات و در گروه `/id` بفرستد. سپس، در حالی که نمونهٔ دیگری از ربات اجرا نیست:

```bash
python3 /opt/sans/run.py --discover-ids
```

این فرمان شناسهٔ گفتگو و فرستنده را از پیام‌های اخیر چاپ می‌کند؛ متن پیام یا توکن را چاپ نمی‌کند. با این اطلاعات `ADMIN_GROUP_ID` را تکمیل کنید. در رباتِ در حال اجرا هم `/id` در دسترس است.

فقط گروهی که `ADMIN_GROUP_ID` مشخص می‌کند فعال است و همهٔ اعضای آن گروه، بدون نیاز به فهرست شناسه‌ها، ادمین محسوب می‌شوند. پیام، منشن، ریپلای، دستور، مدیا و دکمه از هر گروه یا سوپرگروه دیگر نادیده گرفته می‌شود؛ گفت‌وگوهای خصوصی برای قابلیت‌های عادی کاربران فعال می‌مانند. اگر می‌خواهید در گفت‌وگوی خصوصی با ربات هم اختیارات ادمین داشته باشید، `ADMIN_ACCESS=allowlist` بگذارید و شناسهٔ خودتان را در `ADMIN_USER_IDS` بنویسید؛ این تنها راه دسترسی ادمین در خصوصی است. این دسترسی از اطلاعات فرستنده/گفتگوی ارسالی API بله استفاده می‌کند، نه استعلام مستقل عضویت در هر کلیک. دسترسی به خود گروه، لینک دعوت و اضافه‌شدن اعضای جدید را محدود کنید؛ اعضای جدید هم بلافاصله این دسترسی را خواهند داشت.

### ساخت دیتابیس و اجرا

```bash
python3 /opt/sans/run.py --init
python3 /opt/sans/run.py
```

ساخت جداول خودکار است؛ `--init` برای بررسی آفلاین مفید است و توکن نمی‌خواهد. برنامه با long polling اجرا می‌شود؛ پورت ورودی عمومی نیاز ندارد. خروج با `Ctrl+C` است. برای اجرای دائمی از مدیر سرویس سرورتان استفاده کنید.

اگر قبلاً برای همین توکن webhook تنظیم کرده‌اید، ابتدا از API بله `deleteWebhook` را فراخوانی کنید. برنامه webhook موجود را خودکار حذف نمی‌کند. فقط **یک نمونهٔ فعال** برای هر توکن/دیتابیس داشته باشید؛ قفل محلی جلوی اجرای هم‌زمان روی یک دیتابیس را می‌گیرد، نه استفادهٔ همان توکن روی سرور دیگر.

### اجرای محلی برای توسعه

روی ماشین توسعه (بدون systemd و بدون root) همین مخزن کافی است:

```bash
git clone https://github.com/OWNER/sans.git
cd sans
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env && chmod 600 .env
.venv/bin/python3 run.py --init
.venv/bin/python3 run.py
```

روی ویندوز، مسیر مفسر `.venv\Scripts\python.exe` است (مثلاً `.venv\Scripts\python.exe run.py`).

`BALE_BOT_TOKEN`، `ADMIN_GROUP_ID` و کلید/مدل AI را در `.env` بگذارید. فایل `.env`، پوشهٔ `data/` و همهٔ `*.sqlite3*` در git نیستند؛ برای کار روی دادهٔ واقعی، `data/sans.sqlite3` را جداگانه (مثلاً با `scp`) کپی کنید و همان مقدار `DATABASE_PATH` را تنظیم کنید (فایل `data/sans.sqlite3.lock` را کپی نکنید). روی ویندوز، بستهٔ `tzdata` در `requirements.txt` لازم است تا `Asia/Tehran` شناسایی شود.

تست‌ها توکن و شبکه لازم ندارند:
```bash
python3 -m unittest discover -s tests -t . -v
python3 -m compileall -q app tests
```

برای هر توکن فقط **یک** نمونهٔ long polling اجرا کنید. پیش از اجرای محلی، سرویس سرور را متوقف نگه دارید (`systemctl stop sans-bot.service`)؛ قفل محلی فقط جلوی دو نمونه روی یک دیتابیس را می‌گیرد، نه همان توکن روی دو ماشین.

### اجرای دائمی با systemd (کاربر اختصاصی)

نمونهٔ سرویس در `deploy/sans-bot.service` است. یک نمونهٔ امن برای سرور است: کاربر اختصاصی `sans`، کد فقط خواندنی، و نوشتن محدود به پوشهٔ داده. مسیرها (`/opt/sans`) و کاربر/گروه را متناسب با نصب خودتان تغییر دهید.

```bash
sudo useradd --system --home /opt/sans --shell /usr/sbin/nologin sans
sudo chown -R sans:sans /opt/sans
sudo install -m 644 /opt/sans/deploy/sans-bot.service /etc/systemd/system/sans-bot.service
sudo systemctl daemon-reload
sudo systemctl enable --now sans-bot.service
sudo systemctl status sans-bot.service --no-pager
journalctl -u sans-bot.service -n 30 --no-pager
```

پس از تغییر `.env`، دستور `sudo systemctl restart sans-bot.service` را اجرا کنید. برای ورود CSV یا بکاپ، ابتدا `sudo systemctl stop sans-bot.service` و پس از پایان `start` بزنید؛ ابزارهای نگهداری (`--backup`، `--import-*`، `--reconcile`) قفل نصب را می‌گیرند و با ربات در حال اجرا کار نمی‌کنند. گزینهٔ `--discover-ids` را هم‌زمان با سرویس اجرا نکنید.

اعتبار کلید یا دریافت فهرست مدل‌ها، تضمین موفقیت chat/completions نیست. در InferHub شناسهٔ مدل ممکن است به پیشوند ارائه‌دهنده مثل `ali/qwen3.8-flash` نیاز داشته باشد. خطای HTTP 402 با پیام `no provider's ask matches your max-per-mtok bid` به پیدا نشدن ارائه‌دهنده در سقف قیمت پیشنهادی اشاره دارد. تنظیمات قیمت/مسیریابی حساب را نزد سرویس بررسی کنید؛ ربات سقف هزینه را خودکار افزایش نمی‌دهد. در زمان خطای AI، فرمان‌های قطعی همچنان در دسترس‌اند.

### اجرای دائمی بدون root (systemd --user)

اگر ربات با کاربر عادی (نه root) اجرا می‌شود، از سرویس کاربر استفاده کنید تا هم به sudo نیاز نباشد و هم بعد از ریبوت خودکار بالا بیاید. مسیرها را با مسیر واقعی مخزن جایگزین کنید:

```bash
mkdir -p ~/.config/systemd/user
$EDITOR ~/.config/systemd/user/sans-bot.service
systemctl --user daemon-reload
systemctl --user enable --now sans-bot.service
loginctl enable-linger "$USER"      # بدون این، سرویس با خروج از سیستم می‌خوابد
```

نمونهٔ یونیت (مقادیر `WorkingDirectory`، `ExecStart` و مسیر لاگ را با مسیر خودتان تطبیق دهید):

```ini
[Unit]
Description=Bale football session manager (sans)
Wants=network-online.target
After=network-online.target
StartLimitIntervalSec=300
StartLimitBurst=10

[Service]
Type=simple
WorkingDirectory=/home/USER/projects/sans
ExecStart=/home/USER/projects/sans/.venv/bin/python3 /home/USER/projects/sans/run.py
Restart=always
RestartSec=15
TimeoutStopSec=20
UMask=0077
Environment=PYTHONUNBUFFERED=1
# Bale مستقیم پاسخ می‌دهد ولی chat/completions ارائه‌دهندهٔ AI فقط از طریق
# پروکسی محلی کار می‌کند؛ پس Bale از پروکسی مستثنا و AI از آن رد می‌شود.
Environment=http_proxy=http://127.0.0.1:10808
Environment=https_proxy=http://127.0.0.1:10808
Environment=HTTP_PROXY=http://127.0.0.1:10808
Environment=HTTPS_PROXY=http://127.0.0.1:10808
Environment=no_proxy=tapi.bale.ai,localhost,127.0.0.1
Environment=NO_PROXY=tapi.bale.ai,localhost,127.0.0.1
StandardOutput=append:/home/USER/projects/sans/data/logs/bot.log
StandardError=append:/home/USER/projects/sans/data/logs/bot.log

[Install]
WantedBy=default.target
```

```bash
systemctl --user status sans-bot.service --no-pager
tail -f data/logs/bot.log
```

سرویس کاربر محیط پوستهٔ شما را به ارث نمی‌برد؛ هر متغیری مثل پروکسی که ربات لازم دارد باید در خود یونیت با `Environment=` بیاید. اگر پروکسی محلی خاموش باشد، polling بله همچنان کار می‌کند (چون در `no_proxy` است) و فقط پاسخ‌های AI خطا می‌دهند.

### تفکیک مسیر شبکه (هر دو مقصد از پروکسی، فقط loopback مستقیم)

در ۲۰۲۶-۱۰-۲۲ روی همین سرور اندازه‌گیری شد که `tapi.bale.ai` مستقیم سریع‌تر پاسخ می‌دهد و `api.inferhub.dev` فقط از طریق پروکسی محلی جواب می‌دهد؛ برای همین `tapi.bale.ai` در `no_proxy` گذاشته شده بود.

در ۲۰۲۶-۱۰-۲۴ حل نام (DNS) روی این هاست از کار افتاد. نتیجه مستقیمش این بود:

```text
curl: (6) Could not resolve host: tapi.bale.ai
```

ربات چون بله را مستقیم صدا می‌زد، در استارت با `Network error or invalid JSON response` می‌مرد، systemd ده بار ری‌استارت می‌کرد و بعد `Start request repeated too quickly` می‌شد (`systemctl --user is-active sans-bot` مقدار `failed` می‌داد).

پروکسی محلی نام‌ها را در خروجی خودش حل می‌کند، پس حالا **هر دو مقصد** از پروکسی می‌روند و فقط loopback دور زده می‌شود:

```ini
Environment=no_proxy=localhost,127.0.0.1
Environment=NO_PROXY=localhost,127.0.0.1
```

اندازه‌گیری دوباره در ۲۰۲۶-۱۰-۲۴: `getMe` از طریق پروکسی در حدود یک ثانیه `{"ok":true}` برمی‌گرداند. اگر روزی DNS درست شد و خواستید بله را دوباره مستقیم ببرید، اول با `getent hosts tapi.bale.ai` مطمئن شوید که نام حل می‌شود، بعد `no_proxy` را برگردانید.

تشخیص سریع وقتی ربات بالا نمی‌آید:

```bash
systemctl --user is-active sans-bot
journalctl --user -u sans-bot -n 20 --no-pager
. ./.env && curl -sS --proxy http://127.0.0.1:10808 "https://tapi.bale.ai/bot${BALE_BOT_TOKEN}/getMe"
```

### بازیابی پس از خاموشی غیرتمیز

اگر ربات بدون `systemctl stop` کشته شود، ممکن است انتهای `data/logs/bot.log` با بایت‌های `NUL` پر شود. پیش از استارت دوباره فایل را جابه‌جا کنید:

```bash
mv data/logs/bot.log data/logs/bot.log.1
```

پیش از هر راه‌اندازی مجدد پس از حادثه، یک بکاپ بگیرید (ربات باید متوقف باشد، چون بکاپ قفل نصب را می‌گیرد):

```bash
systemctl --user stop sans-bot.service
.venv/bin/python run.py --backup data/backups/pre-restart-$(date +%F).sqlite3
systemctl --user start sans-bot.service
```

پیام‌هایی که در زمان خواب ربات رسیده‌اند از بین نمی‌روند: مقدار `offset` در جدول `settings` ذخیره می‌شود و اولین polling پس از استارت آن‌ها را پردازش می‌کند.

## ورود اطلاعات قبلی

ساختار نمونه در `/opt/sans/examples/players.csv` آمده است. فایل UTF-8 با سرستون‌های زیر بسازید:

```csv
name,opening_balance,note
علی رضایی,300000,بدهی دو سانس قبلی
رضا محمدی,0,
محمد احمدی,-50000,بستانکاری قبلی
```

عدد مثبت یعنی بدهکار، منفی یعنی بستانکار. همهٔ مبلغ‌ها **تومان** هستند. حساب بله لازم نیست؛ بعداً هنگام معرفی و تأیید ادمین متصل می‌شود.

پس از قرار دادن اطلاعات واقعی خودتان در `/opt/sans/players.csv`، ربات را متوقف و اجرا کنید:

```bash
python3 /opt/sans/run.py --import-players /opt/sans/players.csv
```

برای snapshot حساب اعضا از فایل Excel نیز می‌توان استفاده کرد:

```bash
python3 /opt/sans/run.py --import-players '/opt/sans/football-account(1).xlsx'
```

در Excel، مبالغ ستون «مجموع بدهکاری» هزار تومان هستند و به تومان تبدیل می‌شوند. بدهی هر ردیف همیشه از فرمول `(جلسات آمده − جلسات پرداخت‌شده) × ۱۵۰٬۰۰۰ تومان` ساخته می‌شود؛ اگر ستون بدهی پر باشد ولی با این فرمول نخواند، ورود با نام همان ردیف متوقف می‌شود تا ابتدا اکسل اصلاح شود. توضیح همهٔ بدهی‌های این snapshot `بدهی تا ۱۶ مرداد ۱۴۰۵` ثبت می‌شود. ورود Excel snapshot قبلیِ opening را جایگزین می‌کند، روی بدهی‌های سانس‌ها و پرداخت‌های ثبت‌شده دست نمی‌زند، تراکنشی است و اجرای دوبارهٔ همان فایل مبلغ را جمع نمی‌کند.

### بازسازی دوره از سانس‌های واقعی (SPEC-022)

Snapshot برای دورهٔ «تا ۱۶ مرداد ۱۴۰۵» کافی نیست، چون نمی‌گوید کدام بدهی برای کدام سانس است. جای آن، ده سانس واقعی ساخته می‌شود و حضور و پرداخت از روی همان لیست و همان اکسل می‌آید:

```bash
systemctl --user stop sans-bot.service
python3 /opt/sans/run.py --import-sessions /opt/sans/data/sessions.csv --dry-run
python3 /opt/sans/run.py --import-sessions /opt/sans/data/sessions.csv \
  --alias "عباس رسولی=رسولی" --alias "محمد مهدی سبحانی=سبحانی" \
  --allow-new "رفیق علی بختیاری" --allow-new "امین"
python3 /opt/sans/run.py --import-payments '/opt/sans/football-account.xlsx' \
  --workbook-overrides /opt/sans/data/workbook-overrides.csv
python3 /opt/sans/run.py --reconcile '/opt/sans/football-account.xlsx' \
  --workbook-overrides /opt/sans/data/workbook-overrides.csv
systemctl --user start sans-bot.service
```

این چهار فرمان هم مثل بکاپ قفل نصب را می‌گیرند، پس ربات باید متوقف باشد؛ وگرنه با «ربات یا ابزار ورود اطلاعات دیگری در حال اجراست» رد می‌شوند.

قالب آمادهٔ لیست حضور در `examples/sessions-template.csv` است: ردیف اول نام‌ها (همان ۵۱ نام اکسل) و ستون‌های بعدی تاریخ سانس‌ها. هر خانهٔ پر یعنی آن نفر در آن سانس بوده و عدد داخلش تعداد مهمان اوست؛ خانهٔ خالی یعنی نبوده. `x`، `✓`، `حاضر` و `بله` هم یعنی «بدون مهمان»، و `-` یا `غایب` یعنی نبوده. قالب بلند `date,name,guests` هم پذیرفته می‌شود.

لیست پرشدهٔ همین دوره در `data/sessions.csv` است: ۵۲ نام (۵۱ ردیف اکسل به‌علاوهٔ «علی صدری») و ده ستون جمعه. سه جمعهٔ اول خانه‌به‌خانه از دفتر واقعی دیتابیس آمده است؛ در هفت جمعهٔ بعد، جمع هر نفر (اکسل + اصلاح‌های تأییدشده) و تعداد نفرات هر سانس (۱۵، ۲۲، ۱۳، ۱۸، ۱۲، ۱۵ و ۱۴) دقیق است، ولی چون لیست اصلی هر سانس آرشیو نشده بود، این‌که کدام نفر در کدام جمعه بوده **بازسازی** شده است. پول، جمع‌ها و `--reconcile` از این بازسازی اثر نمی‌گیرند.

قواعد ایمنی این سه فرمان:

- تاریخ هر سانس باید **جمعه** باشد؛ همهٔ سانس‌های این دوره ساعت ۱۶:۳۰ در «سالن ورزشی نمونه» با هزینهٔ زمین ۲٬۵۰۰٬۰۰۰ تومان و سهم نفر ۱۵۰٬۰۰۰ تومان ثبت می‌شوند (`--hour`، `--venue-cost` و `--session-fee` قابل تغییرند).
- هیچ ردیفی حذف نمی‌شود. حضور و دفتر فقط **تفاضلی** به‌روز می‌شوند: نفر تازه اضافه می‌شود، تغییر مهمان یک ردیف اصلاح می‌گیرد و حذف یک نفر با یک ردیف اصلاح منفی ثبت می‌شود.
- سانس قدیمی که تاریخش غلط است اصلاح می‌شود، نه دوباره ساخته؛ مثلاً «سانس ۹ خرداد» به «سانس ۸ خرداد» با `session_at` درست تبدیل می‌شود و مبلغ‌هایش دست نمی‌خورد.
- نامی که به یک بازیکن موجود شبیه است خودکار ثبت نمی‌شود؛ با `--alias "نام لیست=نام ذخیره‌شده"` بگویید یکی هستند (نام ذخیره‌شده اصلاح و تاریخچه‌اش حفظ می‌شود) یا با `--allow-new "نام لیست"` بگویید فرد جدیدی است.
- `--dry-run` هیچ‌چیز را ذخیره نمی‌کند و `--reconcile` فقط می‌خواند. تفاضل هر نفر و جمع کل باید صفر شود؛ `--reconcile` تا وقتی همهٔ ردیف‌های اکسل با دفتر نخوانند با کد خطا خارج می‌شود.
- فایل `data/workbook-overrides.csv` اصلاح‌های تأییدشدهٔ اپراتور را **بدون دست‌زدن به خود اکسل** اعمال می‌کند: ستون‌های `name,attended,paid` و ستون اختیاری `debt` (هزار تومان). اگر `debt` نوشته شود باید با `(آمده − پرداخت) × ۱۵۰٬۰۰۰` بخواند، وگرنه ورود متوقف می‌شود؛ نام تکراری هم ورود را متوقف می‌کند. ردیفی که در اکسل نیست با همین فایل اضافه می‌شود (در این دوره «علی صدری»). این گزینه فقط همراه `--import-payments` یا `--reconcile` معنا دارد و به‌تنهایی رد می‌شود. با اصلاح‌های تأییدشده جمع اکسل ۱۹٬۰۵۰٬۰۰۰ تومان است، نه ۱۷٬۷۰۰٬۰۰۰.
### مهمان: همیشه روی حساب میزبان (SPEC-024)

مهمان هیچ‌وقت حساب جداگانه ندارد: تعدادش روی ردیف میزبان در همان سانس می‌نشیند و بدهی هر ردیف `(خود فرد + تعداد مهمان) × سهم هر نفر` است. اگر خودِ میزبان در آن سانس نبوده، ردیف با `own=0` فقط سهم مهمان را بدهکار می‌کند.

نام مهمان **اختیاری** است: اگر ادمین اسم را بگوید ثبت می‌شود، وگرنه فقط تعداد می‌ماند. مهمان همیشه یک سهم کامل دارد:

```text
/do {"action":"attendance","args":{"session":3,"player":15,"guests":2,"guest_names":["رضا","علی"]}}
```

- `guest_names` نباید از `guests` بیشتر باشد و نام خالی یا تکراری پذیرفته نمی‌شود؛ چنین خطایی هیچ ردیفی ثبت نمی‌کند (fail closed).
- اگر `guests` را نگویید ولی اسم‌ها را بگویید، تعداد از شمار اسم‌ها حساب می‌شود.
- اسم مهمان فقط توصیفی است: در نمایش کامل سانس (فقط ادمین) و در پیش‌نمایش نهایی‌سازی دیده می‌شود و بدهی را تغییر نمی‌دهد.
- برداشتن حضور (`present=false`) نام مهمان‌های همان ردیف را هم پاک می‌کند تا ردیف یتیم نماند.

برای جمع‌کردن مهمان‌های امروزی (۱۰ نام در `data/guest-links.csv`) زیر حساب میزبان‌شان:

```bash
systemctl --user stop sans-bot.service
python3 /opt/sans/run.py --migrate-guests /opt/sans/data/guest-links.csv --dry-run
python3 /opt/sans/run.py --migrate-guests /opt/sans/data/guest-links.csv
python3 /opt/sans/run.py --reconcile '/opt/sans/football-account.xlsx' \
  --workbook-overrides /opt/sans/data/workbook-overrides.csv
systemctl --user start sans-bot.service
```

قواعد این مهاجرت:

- مهمان روی حساب **میزبان** می‌آید، نه حساب خودش؛ حساب خالی مهمان بعد از انتقال حذف می‌شود و نامش در «مهمان‌های بانام» و در `audit_logs` می‌ماند.
- اگر میزبان در سانس مهمان حاضر بوده همان سانس؛ وگرنه **نزدیک‌ترین سانسی که خودِ میزبان حضور داشته** و در تساوی فاصله **سانس قبلی** برنده است.
- اگر میزبان هیچ حضوری نداشته باشد، ردیف مهمان‌دار با `own=0` در سانس خودِ مهمان ساخته می‌شود تا فقط سهم مهمان بدهکار شود (نه سهم خود میزبان).
- جمع دفتر **تغییر نمی‌کند** (۱۹٬۰۵۰٬۰۰۰ تومان): ردیف‌های دفتر مهمان به میزبان منتقل می‌شوند، نه اینکه سهم تازه‌ای ساخته شود.
- اجرای دوباره بی‌اثر است، `--dry-run` هیچ‌چیز نمی‌نویسد، و مهمان ناشناس یا «مهمان نواز» کل عملیات را متوقف می‌کند.
### پیوند حساب‌ها برای گزارش مشترک و تسویهٔ همدیگر (SPEC-025)

برای برادر، پسر یا دوست نزدیکی که برای هم پول می‌دهند، می‌توان دو یا چند حساب را «پیوند» کرد. پیوند **قرینه** است: اگر A به B وصل شود، B هم A را می‌بیند. پیوند فقط اجازهٔ **دیدن خلاصه و پیشنهاد تسویه** می‌دهد؛ هیچ پولی خودکار جابه‌جا نمی‌شود.

```bash
# ادمین در گروه مدیریتی (هر کدام یک کارت تأیید می‌سازد)
/link2 12 18         # وصل‌کردن دو حساب
/unlink2 12 18       # برداشتن پیوند
/links               # فهرست پیوندهای فعلی
/suggestlinks        # پیشنهاد زوج‌ها بر اساس فامیل یکسان

# بازیکن در چت خصوصی
/requestlink حسن رضایی   # درخواست وصل‌شدن؛ به کارت تأیید ادمین می‌رود
/debt                     # گزارش خود + بلوک «حساب‌های پیوندی»
/card                     # شمارهٔ کارت + همان بلوک «حساب‌های پیوندی» (SPEC-029)
/settlepartner حسن رضایی  # درخواست تسویهٔ طرف مقابل؛ باز هم با تأیید ادمین
```

قواعد:

- **هیچ پیوندی بدون کلیک «تأیید» ساخته نمی‌شود**؛ درخواست بازیکن فقط یک کارت در گروه مدیریتی می‌سازد.
- گزارش طرف مقابل فقط **نام، مانده و وضعیت** را نشان می‌دهد؛ گردش کامل دفتر، شمارهٔ تماس و رسیدهای او خصوصی می‌ماند. همین خلاصه (id، نام، مانده) و نه بیشتر به مدل هم داده می‌شود.
- همان خلاصه در پاسخ `/card` هم می‌آید تا بازیکن پیش از واریز، هم شمارهٔ کارت و هم ماندهٔ پیوندها را یک‌جا ببیند؛ اگر کارت هنوز ثبت نشده باشد، فقط پیام درخواست از ادمین می‌آید (SPEC-029).
- تسویهٔ طرف مقابل یک پیشنهاد `settle` است؛ تا ادمین تأیید نکند هیچ ردیفی در دفتر ثبت نمی‌شود و اگر مانده‌اش تغییر کرده باشد، کارت با همان قاعدهٔ SPEC-011 منقضی می‌شود.
- `/suggestlinks` فقط **فامیل یکسان** را پیشنهاد می‌دهد (نه واژه‌های نسبت مثل «دوست»، «شاگرد»، «بچه‌های» و نه نام‌های تک‌کلمه‌ای). تشخیص فامیل یکسان یعنی «شاید یک خانواده»؛ پیوند هرگز از روی حدس ساخته نمی‌شود.
- پیوند گذرا (A–B و B–C ⇒ دیدن C) وجود ندارد؛ فقط پیوند مستقیم.
- حذف یا ادغام بازیکن پیونددار، پیوند او را به بازیکن باقی‌مانده منتقل می‌کند و هرگز پیوندِ بی‌صاحب باقی نمی‌گذارد.


- `--reconcile` بعد از مهاجرت سبز می‌ماند: ردیف اکسل هر نامِ منتقل‌شده به میزبانش نسبت داده می‌شود و خود اکسل دست‌نخورده می‌ماند.

ورود فایل تراکنشی است: هر خط نامعتبر باشد کل ورود برمی‌گردد. ورود تکراری همان فایل دوباره بدهی ایجاد نمی‌کند. تغییر ماندهٔ اولیهٔ واردشده مجاز نیست؛ اصلاح مالی را از ربات با دلیل ثبت کنید. نام کامل باید یکتا باشد؛ برای هم‌نام‌ها پسوند متمایز بگذارید. ورود اولیه تاریخچهٔ سانس‌های گذشته را بازسازی نمی‌کند؛ یک «ماندهٔ اولیه» با توضیح می‌سازد.

**فایل واقعی اعضا را وارد Git نکنید.** بهتر است آن را در `/opt/sans/data/players.csv` که نادیده گرفته می‌شود نگهداری کنید و مسیر فرمان را مطابق آن تغییر دهید.

## گردش کار ادمین

در گروه، ربات تنها به فرمان‌های `/...`، ریپلای به خودش، منشن نام کاربری‌اش یا پیام‌های دارای واژهٔ `مسئول` پاسخ می‌دهد؛ مکالمات عادی گروه را به AI نمی‌فرستد.

سلام خالی هم مثل یک پیام آزاد به AI می‌رود و پاسخ کوتاه می‌گیرد؛ در گروه فقط سلامِ خطاب‌شده (مثلاً «مسئول سلام») پاسخ داده می‌شود. سلام خالی هیچ عملیات یا پیشنهادی نمی‌سازد و اگر سرویس AI پاسخ معتبر ندهد، یک پاسخ کوتاه ثابت می‌فرستد.

مثال‌ها:

```text
مسئول، یک سانس به اسم پنجشنبه ۲۳ مهر ثبت کن؛ ساعت ۲۱، زمین آزادی؛ هزینه زمین ۲۴۰۰۰۰۰ تومان و سهم هر نفر ۱۵۰۰۰۰ تومان.
مسئول، علی رضایی در سانس پنجشنبه ۲۳ مهر با دو مهمان آمد و رضا محمدی تنها آمد.
مسئول، حساب سانس پنجشنبه ۲۳ مهر را نهایی کن.
مسئول، بدهی علی رضایی چقدر است؟
مسئول، توضیح علی رضایی را بگذار «این مبلغ شامل سهم مهمان‌ها هم هست».
مسئول، شماره کارت را به ۶۰۳۷... به نام صاحب حساب تغییر بده.
```

ربات خلاصهٔ عملیات را برای تأیید نشان می‌دهد. **قبل از تأیید، مبلغ، واحد، نام، تاریخ و تعداد مهمان را بررسی کنید**؛ مدل ممکن است اشتباه کند. برای عدد مبهم مثل «۱۵۰ تومن» باید مقدار دقیق اعلام شود. زمان سانس جدید به‌صورت ISO با timezone تهران ذخیره می‌شود؛ `when_text` متن اصلی کاربر است و سانس‌های قدیمی بدون زمان ساختاری مهاجرت خودکار نمی‌شوند. تاریخ‌ها را می‌توان شمسی نوشت: «۹ خرداد ساعت ۲۱»، «۹ خرداد ۱۴۰۴ ساعت ۲۱» یا «۱۴۰۵/۰۳/۰۹ ۲۱:۰۰»؛ اگر سال ننویسید سال جاری شمسی در نظر گرفته می‌شود. تاریخ‌های نسبی «امروز»، «فردا»، «پس‌فردا»، روزهای هفته و تاریخ میلادی `YYYY-MM-DD` هم پشتیبانی می‌شوند. ساعت‌های مبهم مثل «۹» یا بازهٔ مبهم «عصر» پذیرفته نیستند. ترجیحاً تاریخ و ساعت ۲۴ساعته بنویسید. تاریخ‌ها در پاسخ‌ها و فهرست سانس‌ها شمسی نمایش داده می‌شوند.

### محاسبهٔ بدهی

```text
بدهی شخص در یک سانس = سهم ثابت همان سانس × (۱ + تعداد مهمان‌ها)
```

مثلاً سهم ۱۵۰٬۰۰۰ تومان و دو مهمان یعنی ۴۵۰٬۰۰۰ تومان. مبلغ ۲٬۴۰۰٬۰۰۰ تومان زمین فقط برای گزارش هزینه است و در این فرمول نقشی ندارد.

۱. سانس را با زمان دقیق (مثلاً «فردا ساعت ۲۱» یا «پنجشنبه ۲۱:۳۰») بسازید و سهم هر نفر را مشخص کنید؛ هزینهٔ زمین اختیاری است.
۲. حضورها را ثبت/اصلاح کنید. ثبت مجدد حضور، تعداد مهمان را **جایگزین** می‌کند.
۳. با درخواست «نهایی کن»، خلاصهٔ تمام بدهی‌های پیشنهادی را ببینید و تأیید کنید.
۴. در این مرحله بدهی ثبت و به بازیکن‌های دارای حساب متصل اطلاع داده می‌شود.

تا قبل از نهایی‌سازی، حضور بدهی ایجاد نمی‌کند. پس از نهایی‌سازی، حضور و سهم سانس قفل هستند؛ برای اصلاح، یک تراکنش اصلاح حساب با توضیح ثبت کنید تا سابقه پاک نشود. سانس جدید مبلغ مستقل دارد. اگر چند سانس باز باشد ربات عنوان/شناسهٔ دقیق می‌پرسد؛ حدس نمی‌زند.

### فرمان‌های مستقل از AI

راهنمای `/help` عمداً هیچ فرمانی نشان نمی‌دهد و فقط می‌گوید ربات چه کارهایی را به فارسی معمولی انجام می‌دهد. ادمین در گروه مدیریتی و در پیوی خودش فقط «راهنمای مدیریت» را می‌بیند و بازیکن فقط راهنمای بازیکن را؛ این دو هرگز با هم ترکیب نمی‌شوند. ماندهٔ حساب هم در پیام جداگانه‌ای، بعد از راهنما، فرستاده می‌شود تا متن راهنما ثابت و کوتاه بماند.

جدول زیر فقط برای کسانی است که فرمان را از حفظ می‌دانند؛ همهٔ این کارها با جملهٔ فارسی هم انجام می‌شود.

اگر فرمانی را اشتباه بنویسید، ربات فقط یک خط می‌گوید: «این دستور را نمی‌شناسم» و راهنمای کامل را نمی‌فرستد؛ چون راهنمای کامل شبیه «انجام شد» دیده می‌شد و غلطِ تایپی معلوم نمی‌شد. همین پیام برای فرمان ادمینی هم می‌آید که بازیکن بفرستد، پس معلوم نمی‌شود چنین فرمانی برای کسی دیگر وجود دارد. اگر فرمانی مقدار لازم داشته باشد و بدون آن فرستاده شود (`/confirm`، `/approve`، `/identify`، `/amount`)، ربات شکل درست همان فرمان را نشان می‌دهد. نام فرمان به بزرگی و کوچکی حروف حساس نیست (`/Help` هم کار می‌کند) و `/help@نام_ربات` مثل قبل کار می‌کند.

### اصلاح هویت بازیکن

اگر هنگام ورود اطلاعات قدیمی نام کوتاه یا ناقص ثبت شده باشد، سه راه دارید:

- **تغییرنام:** `/rename 15 محمد مهدی موحد` یا «مسئول، اسم بازیکن ۱۵ رو بکن محمد مهدی موحد». شناسه و همهٔ سوابق حفظ می‌شود.
- **ادغام:** `/merge 12 18` رکورد ۱۲ را در ۱۸ ادغام می‌کند؛ حضور، دفترکل و رسیدها منتقل و رکورد تکراری حذف می‌شود. ادغام همیشه دکمهٔ تأیید دارد.
- **حذف:** `/delplayer 4` فقط برای رکوردی که هیچ حضوری ندارد. اگر تاریخچه داشته باشد، ربات پیشنهاد ادغام می‌دهد.

ربات دیگر برای نام ناشناس در ثبت حضور بازیکن نمی‌سازد؛ اگر نام با یک بازیکن موجود مشابه باشد، همان‌ها را با `#شناسه` نشان می‌دهد و نام کامل را می‌پرسد. ادغام در این حالت‌ها انجام نمی‌شود: هر دو بازیکن به یک حساب بله متصل باشند، درخواست منتظری به آن‌ها اشاره کند، یا مهمان‌های رکورد تکراری از رکورد اصلی بیشتر باشد (خطر گم‌شدن مهمان). پس از ادغام، ادامهٔ گفت‌وگو به بازیکن باقی‌مانده اشاره می‌کند و پس از حذف، اشارهٔ قبلی پاک می‌شود؛ ارجاع به بازیکن حذف‌شده هرگز به مدل فرستاده نمی‌شود.

برای انجام تغییرات بدون AI از `/do` با JSON استفاده کنید؛ همچنان تأیید لازم است:

```text
/do {"action":"new_player","args":{"name":"علی رضایی","note":""}}
/do {"action":"new_session","args":{"title":"پنجشنبه ۲۳ مهر","when_text":"پنجشنبه ساعت ۲۱","location":"آزادی","venue_cost":2400000,"person_fee":150000}}
/do {"action":"attendance","args":{"session":1,"player":1,"guests":2}}
/do {"action":"attendance","args":{"session":1,"player":1,"present":false}}
/do {"action":"finalize","args":{"session":1}}
/do {"action":"adjustment","args":{"player":1,"amount":-50000,"note":"تخفیف با توافق ادمین"}}
/do {"action":"settings","args":{"key":"card","value":"شماره کارت و نام صاحب حساب"}}
/do {"action":"settings","args":{"key":"payment_note","value":"لطفاً تا جمعه تسویه کنید؛ بعد از واریز رسید بفرستید."}}
/do {"action":"settings","args":{"key":"approval_required","value":false}}
```

دستورهای دسته‌ای تا ۲۰ حضور یا بازیکن جدید پشتیبانی می‌شوند؛ هر دسته اتمی است. ثبت بازیکن و استفاده از شناسهٔ جدیدش در همان دسته پشتیبانی نمی‌شود. ابتدا بازیکن‌ها را بسازید.

## گردش کار بازیکن و رسید

۱. اولین پیام خصوصی کاربر (دستور `/start` یا «سلام») را خود ربات و بدون AI جواب می‌دهد و فقط دو چیز می‌خواهد: نام و نام خانوادگی کامل، و شمارهٔ موبایل با دکمهٔ «ارسال شمارهٔ من». این پیام یک‌بار برای هر حساب فرستاده می‌شود و شماره و نام هرگز از کاربر دوباره پرسیده نمی‌شود. از پیام دوم به بعد مدل گفتگو را ادامه می‌دهد؛ اگر نام کاربر با یک بازیکن ثبت‌شده جور باشد، مدل همان را پیشنهاد می‌دهد و بعد از تأیید کاربر درخواست را می‌فرستد.
۲. کاربر نام کاملش را می‌گوید یا `/identify علی رضایی` می‌فرستد. **کارت ادمین فقط وقتی ساخته می‌شود که هم نام و هم شماره معلوم باشد**؛ اگر شماره‌ای ثبت نشده باشد، ربات همان‌جا نام را نگه می‌دارد و دکمهٔ «ارسال شمارهٔ من» را می‌فرستد. دکمهٔ بله شماره را نمی‌فرستد، فقط هویت را تأیید می‌کند، پس نام و شماره هرگز در یک پیام نمی‌آیند؛ هر کدام اول برسد، ربات منتظر آن یکی می‌ماند و بعد **یک کارت کامل** برای ادمین می‌فرستد. نتیجه: ادمین هر درخواست را یک‌بار می‌بیند، با شماره. اگر کاربر شماره‌اش را نفرستد، کارتی ساخته نمی‌شود؛ `/cancel` نام نگه‌داشته‌شده را فراموش می‌کند. برای اینکه ادمین‌ها بتوانند او را راحت‌تر تشخیص دهند، شمارهٔ contact و username و نام نمایشی فقط در درخواست ادمین نمایش داده می‌شوند. شمارهٔ contact شخص دیگر پذیرفته نمی‌شود. اگر شماره پیش از نام فرستاده شود، در دفترچهٔ مخاطبان می‌ماند و هنگام تأیید اتصال روی بازیکن ثبت می‌شود (شمارهٔ موجود بازنویسی نمی‌شود).
۳. حتی تطبیق دقیق نام نیاز به تأیید ادمین دارد؛ پیش از تأیید، بدهی افشا نمی‌شود. برای نام مبهم، ادمین با `/link` شخص درست را مشخص می‌کند؛ کارت درخواست، نام‌های مشابه را با #شناسه نشان می‌دهد. هیچ فهرست نام خصوصی برای کاربر ناشناس فرستاده نمی‌شود.
برای تطبیق مستقیم ادمین، به پیام profile/contact/forward دارای شناسهٔ عددی ریپلای کنید و در گروه مدیریتی `/bind نام بازیکن [@username]` بفرستید. username فقط کنترل سازگاری است و به‌تنهایی شناسه محسوب نمی‌شود؛ پیام بدون شناسه، شناسهٔ ربات، mismatch یا حساب/بازیکن متصل‌شده رد می‌شود. اتصال تا زدن دکمهٔ تأیید pending می‌ماند.
۴. پس از اتصال، `/start`، `/debt` و پیام فارسی برای حساب خودش کار می‌کنند. `/card` بدون نیاز به تأیید هویت در دسترس است (اگر فرستنده به بازیکنی وصل باشد، بلوک «حساب‌های پیوندی» هم به آن اضافه می‌شود). کاربر عادی نمی‌تواند بدهی دیگران را بگیرد.
۵. عکس/فایل رسید را می‌فرستد و مبلغ دقیق را در کپشن عددی، پیام بعدی یا `/amount 150000` اعلام می‌کند. OCR انجام نمی‌شود.
۶. رسید و مبلغ اعلامی به گروه ادمین‌ها می‌رود. در حالت پیش‌فرض، تا زمان تأیید هیچ مبلغی از بدهی کم نمی‌شود.
۷. تأیید باعث کسر **مبلغ پرداخت** می‌شود، نه پاک‌شدن تمام بدهی. اضافه‌پرداخت بستانکاری ایجاد می‌کند؛ رد رسید مانده را تغییر نمی‌دهد.

در حالت `approval_required=false`، دریافت رسید **همراه مبلغ معلوم** کافی است و پرداخت خودکار ثبت می‌شود. رسیدهای قبلیِ منتظر، با تغییر تنظیم خودکار تأیید نمی‌شوند. `/cancel` رسیدِ هنوز ثبت‌نشده را کنار می‌گذارد، نه پرداخت تأییدشده یا رسید منتظر ادمین را.

**هشدار:** این سیستم به بانک متصل نیست. file_id / file_unique_id تکراری دوباره ثبت نمی‌شود، ولی عکس ویرایش‌شده یا بارگذاری متفاوت ممکن است شناسهٔ دیگری داشته باشد. تشخیص انتقال بانکی تکراری، اصالت تصویر، مبلغ و مقصد بر عهدهٔ ادمین است. رسید ردشده با همان شناسهٔ فایل مجدداً ثبت نمی‌شود؛ برای اشتباه ادمین از اصلاح حساب مستند استفاده کنید.

## حریم خصوصی و قابلیت اطمینان

- AI صرفاً JSON پیشنهاد می‌دهد؛ SQL، تأیید پرداخت یا اجازهٔ دسترسی از مدل پذیرفته نمی‌شود.
- نام ادمین یا جملهٔ «من ادمینم» مجوز نیست؛ فقط گروه مدیریتی تنظیم‌شده مرز دسترسی است. پیام‌های همهٔ گروه‌های دیگر قبل از AI، لاگ و پردازش مدیا رد می‌شوند.
- مدل فقط متن، تاریخچهٔ محدود همان فرستنده/گفتگو و context لازم را می‌گیرد. در گروه فهرست نام/شناسهٔ بازیکن‌ها هم برای تطبیق ارسال می‌شود. عکس رسید برای AI ارسال نمی‌شود. تاریخچه ممکن است شامل ماندهٔ حساب یا شماره کارتِ پاسخ قبلی باشد؛ سرویس قابل اعتماد انتخاب کنید و کاربران را مطلع کنید.
- مرجع فایل رسید در SQLite نگه داشته می‌شود و خود فایل با API بله مجدداً برای ادمین ارسال می‌شود. **بکاپ دیتابیس، آرشیو مستقل تصاویر رسید نیست**؛ ماندگاری دسترسی به رسانه وابسته به بله است.
- پیام‌های ورودی، وضعیت مکالمه، درخواست‌های منتظر و صف خروجی پایدارند. اجرای دوبارهٔ همان update یا تأیید دوباره، تراکنش مالی جدید نمی‌سازد.
- پیام‌های پشت‌سرهم یک نفر (مثلاً «سانس فردا» و بعد «ساعت ۹ لغو شد») تا `TURN_COALESCE_SECONDS` (پیش‌فرض ۱٫۲ ثانیه) در یک نوبت جمع می‌شوند؛ یک اعلان «دریافت شد» و یک پاسخ می‌گیرند. با `TURN_COALESCE_SECONDS=0` این رفتار خاموش می‌شود. دستورهای `/`، رسید تصویری و contact هرگز با متن دیگر جمع نمی‌شوند. حافظهٔ گفتگو ۴۰ نوبت ذخیره و حداکثر ۲۰ پیام اخیر به مدل داده می‌شود.
- پیام «دریافت شد» **فقط وقتی می‌آید که واقعاً کاری در جریان باشد**، یعنی وقتی نوبت به مدل می‌رسد. دستورهای قطعی مثل `/help`، `/card`، `/players`، `/debt`، `/sessions`، `/support` و `/cancel` بدون هیچ اعلانی و بلافاصله جواب می‌گیرند؛ `/start`، سلامِ خالی و پیام‌های غیرمرتبط گروه هم اعلان نمی‌گیرند. عکس و فایل اعلان می‌گیرند، چون آپلود خودش طول می‌کشد. `/identify` هم اعلان می‌گیرد، چون ممکن است تطبیق و ثبت انجام دهد و تا آمدن شماره صبر کند. تشخیص دستور از خودِ فهرست دستورها می‌آید، نه از یک فهرست دوم. وقتی اعلانی می‌آید، تا پایان پردازش می‌ماند و همان یک پیام مرحله‌به‌مرحله ویرایش می‌شود تا کاربر ببیند کار جلو می‌رود: «⏳ در حال بررسی درخواست…»، «🔎 در حال خواندن اطلاعات…»، «✍️ در حال ثبت تغییرات…»، «💬 در حال آماده‌سازی پاسخ…». این ویرایش‌ها مستقیم و خارج از صف خروجی ارسال می‌شوند، پس با خطای شبکه هرگز مانع یا خراب‌کنندهٔ پاسخ نیستند؛ با `PROGRESS_UPDATES=0` خاموش می‌شوند. یک متن تکراری دوباره فرستاده نمی‌شود و فقط متن‌های ثابت همین فهرست اجازهٔ ارسال دارند، پس هیچ داده‌ای (مبلغ، شماره، نام) در آن‌ها نمی‌آید. **پاسخ نهایی همیشه پیام جدید است و پیام روند را ویرایش نمی‌کند؛ بعد از ارسال پاسخ، همان پیام روند پاک می‌شود** تا کاربر فقط پاسخ را ببیند. اگر بله اجازهٔ حذف ندهد (مثلاً پیام قدیمی‌تر از ۴۸ ساعت)، حذف بی‌صدا نادیده گرفته می‌شود و پاسخ دست‌نخورده می‌رسد.
- پیشنهاد تغییرات پس از ۲۴ ساعت یا هر تغییر ثبت‌شدهٔ دیگر منقضی می‌شود؛ دوباره درخواست بدهید تا خلاصهٔ تازه نمایش داده شود. ادمین می‌تواند کارت‌های منتظر را زودتر با `/expire [ساعت]` ببندد (`/expire 0` یعنی همه)؛ بستن کارت هیچ حساب، سانس یا رسیدی را تغییر نمی‌دهد. درخواست هویت تا بررسی/لغو باقی می‌ماند و با این فرمان بسته نمی‌شود.
- ارسال خروجی retry دارد؛ اگر بله پیام را گرفته باشد ولی پاسخ شبکه گم شود، **اعلان ممکن است تکرار شود**؛ تراکنش مالی دوباره اعمال نمی‌شود. خطاهای ارسال در log می‌آیند و پیام در صف باقی می‌ماند.
- یادآوری‌ها هنگام اجرای برنامه بررسی می‌شوند؛ تایمر دقیق تقویمی، پیامک یا پیگیری خارج از بله وجود ندارد. سؤال مشابه در کمتر از ۶ ساعت تکرار نمی‌شود.
- SQLite رمزگذاری‌شده نیست. فایل دیتابیس، بکاپ‌ها، CSV و `.env` را محرمانه نگه دارید. برنامه فایل‌های تازه را با دسترسی خصوصی ایجاد می‌کند.

  schema.sql         مدل داده (FA، معامله‌ای)

  agent.py           گراف LangGraph، ابزارها، پرامپت سیستم
  ai_context.py      ساخت حداقلی و نقش‌آگاه context برای مدل

## تست و اعتبارسنجی

```bash
python3 -m unittest discover -s tests -t . -v
python3 -m compileall -q app tests
git diff --check
```

تست‌ها به توکن، شبکه، دیتابیس واقعی یا کلید AI نیاز ندارند: هر تست یک SQLite موقت می‌سازد و مدل را با یک نمونهٔ جعلی (`FakeAI`) جایگزین می‌کند. صحبت‌های خارجی با بله یا مدل هیچ‌وقت در تست‌ها اجرا نمی‌شوند؛ فقط شکل payload صف خروجی بررسی می‌شود.

## بکاپ و تست

ربات را متوقف کنید. مقصد بکاپ باید جدید باشد:

```bash
python3 /opt/sans/run.py --backup /opt/sans/data/backup-2026-10-15.sqlite3
python3 -m unittest discover -s /opt/sans/tests -t /opt/sans -v
```

بکاپ از API خود SQLite استفاده می‌کند تا WAL باعث نسخهٔ ناقص نشود. برای بازیابی، در حالت توقف از مسیر فایل بکاپ به‌عنوان `DATABASE_PATH` استفاده کنید. فایل‌های WAL قدیمی را کنار دیتابیس جایگزین‌شده رها نکنید.

تست‌ها آفلاین‌اند و از دیتابیس موقت و کلاینت ساختگی استفاده می‌کنند: مهمان‌ها، مانده‌ها، ورود اولیه، اتصال هویت، محدودیت دسترسی، رسیدها، پردازش تکراری، تأیید قدیمی، rollback دسته‌ای و retry شبکه. برای smoke-test واقعی باید توکن بله و تنظیمات سرویس مدل خودتان را بدهید؛ سازگاری مدل انتخابی و دسترسی گروه نیاز به بررسی با همان سرویس دارند.

## مشارکت

این پروژه با یک گردش‌کار سبک مشخصات‌محور (Spec-Driven Development) پیش می‌رود و `AGENTS.md` قرارداد آن است:

```text
spec → plan → implement → test → review
```

هر تغییر غیرجزئی طبق این ترتیب انجام می‌شود:

1. مشخصهٔ مربوط در `specs/` را بخوانید و معیار پذیرش را **قبل** از کد بنویسید.
2. تست اجرایی برای همان معیارها اضافه کنید (`tests/`).
3. کوچک‌ترین تغییری را که تست‌ها را سبز می‌کند بنویسید.
4. هر سه فرمان اعتبارسنجی را اجرا کنید.
5. وضعیت مشخصه و محدودیت‌های باقی‌مانده را ثبت کنید.

`tests/test_spec_contracts.py` این قرارداد را اجباری می‌کند: هر مشخصه باید بخش‌های لازم، شناسه‌های یکتا و **نگاشت به تستی که واقعاً وجود دارد** داشته باشد؛ مشخصهٔ بدون تست، سوئیت را قرمز می‌کند.

```bash
python3 -m unittest discover -s tests -t . -v
python3 -m compileall -q app tests
git diff --check
```

قواعد ثابت پروژه:

- خروجی مدل یک **درخواست** است، نه فرمان؛ قصد/آرگومان/موجودیت نامعتبر باید fail-closed رد شود.
- context مدل حداقلی و نقش‌آگاه بماند؛ فهرست کامل بازیکنان، شماره‌ها، محتوای رسید و `.env` فرستاده نشود.
- قواعد مالی، معنای دفتر کل و شِمای SQLite فقط با مشخصهٔ اختصاصی تغییر کنند.
- فقط کتابخانهٔ استاندارد پایتون و وابستگی‌های موجود در `requirements.txt`.
